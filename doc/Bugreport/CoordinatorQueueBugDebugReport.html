Coordinator Edge 排队预约 Bug Debug 报告

范围：Edge 上已有多个排队任务时，任务因准确率不足失败并触发新一轮调度，随后出现错误的并发超限。

涉及平台文件：mars/coordinator.py

回归测试文件：tests/test_runtime_regressions.py

一句话结论：原 Coordinator 把每个未完成任务的预约结束时间都延长到约 1012 ms，破坏了任务原本依次排队的关系；修复后保留原预约时间，校验器不再把排队任务误判为同时运行。

1. Bug 成因

1.1 正常情况下的预约

Edge 的并发上限是 2。多于两个任务到达时，调度器会为它们安排不同的开始、结束时间。前两个任务可以同时执行，后面的任务在前面任务完成后依次开始。这些时间段就是资源预约。

1.2 原来的代码

原版 mars/coordinator.py 在每轮调度前生成 carry_in，将上一轮仍未完成的预约交给下一轮调度：

_PENDING_COMPLETION_HORIZON_MS = 1_000_000_000_000.0

pending_attempt_ids = {
    active.attempt_id
    for active in active_by_dispatch.values()
    if not active.completion_future.done()
}
carry_in = tuple(
    replace(
        reservation,
        finish_ms=max(
            reservation.finish_ms,
            current_time_ms
            + _PENDING_COMPLETION_HORIZON_MS,
        ),
    )
    if attempt_id in pending_attempt_ids
    else reservation
    for attempt_id, reservation
    in active_resource_reservations.items()
    if (
        attempt_id in pending_attempt_ids
        or reservation.finish_ms
        > current_time_ms + 1e-9
    )
)

这段代码的问题在于：completion_future.done() == False 不只表示“现在正在运行”，也可能表示“已经安排到 Edge、但仍在等待完成通知”。因此，排队任务也被当作需要无限期保护的任务。

1.3 为什么会误报并发超限

假设几个预约本来是前后排列的：

B：0 ～ 20 ms
C：0 ～ 20 ms
D：20 ～ 40 ms
E：20 ～ 40 ms

失败触发重新调度后，原代码把这些尚未完成任务的结束时间全部改成约 1012 ms：

B：0  ～ 1,000,000,000,000 ms
C：0  ～ 1,000,000,000,000 ms
D：20 ～ 1,000,000,000,000 ms
E：20 ～ 1,000,000,000,000 ms

到 20 ms 左右，校验器看到 B、C、D、E 的时间段相互重叠，于是认为四个任务同时占用并发上限为 2 的 Edge，最终抛出 PlanValidationError。实际错误不是 Edge 真正同时运行了四个任务，而是预约时间被错误延长了。

2. Bug 复现过程

回归测试建立了以下确定性场景：

项目设置
设备1 台 Edge
Edge 并发上限2
失败任务a-failing，短任务，启用准确率判断
排队任务b-queued、c-queued、d-queued、e-queued
执行噪声0，避免随机耗时干扰
随机种子0
最大尝试次数2；第一次失败后会触发重试调度

为了稳定复现“失败任务先返回、其他任务完成通知仍在等待”的时序，测试专用 Runtime 只延迟四个排队任务的完成通知 0.01 秒。该类只存在于测试文件，没有修改或替代平台 Runtime。

2.1 修复前的实际结果

  1. a-failing 在约 0.943396 ms 完成并因准确率不足失败。
  2. 失败触发 wf:retry-epoch:2 新一轮调度。
  3. 四个排队预约的结束时间被延长到约 1,000,000,000,000.9434 ms。
  4. 校验器在 18.8679245283 ms 发现重叠预约数量超过 Edge 的 max_concurrency=2。
  5. 测试以 node edge exceeds max_concurrency 失败，Bug 被成功复现。

3. 修改文件 Diff

平台代码只修改了 mars/coordinator.py 的 carry_in 生成逻辑，并删除了不再使用的极远时间常量；没有修改 Runtime、Scheduler 或 Optimizer，也没有新增平台字段、接口或抽象层。

    active.attempt_id

    if attempt_id in active_attempt_ids
)

3.3 修改含义

修改前修改后
复制预约并强行修改 finish_ms直接沿用原预约
多个排队任务可能被误认为长期同时运行保留原来的前后排队关系
准确率失败触发重调度时可能并发超限新调度依据真实的已有预约寻找空闲时间

4. 回归测试文件说明

4.1 测试辅助类

tests/test_runtime_regressions.py 中增加了 _DelayedQueuedCompletionRuntime。它继承现有 InProcessRuntime，唯一作用是延迟指定排队任务的完成通知，从而稳定制造真实系统可能出现的异步返回顺序。它不是平台接口，也不会进入生产调度逻辑。

4.2 回归测试

新增测试函数：

test_accuracy_failure_replanning_preserves_edge_queue()

测试检查三件事：

  1. 准确率失败任务确实进行了两次尝试，证明失败触发了重新调度。
  2. 四个排队任务最终全部成功。
  3. 整个过程没有抛出 Edge 并发超限异常。

4.3 验收结果

修复前：新增回归测试失败，成功复现 node edge exceeds max_concurrency。

修复后：同一个回归测试 1 passed。

相关测试集：test_coordinator.py、test_coordinator_planning.py、test_runtime_regressions.py 合计 25 passed。

5. 最终结论

本次修复没有关闭准确率失败判断，也没有绕过并发校验。它只纠正了 Coordinator 传递旧预约的方式：未完成任务继续保留原调度时间，不再被统一延长到极远时间。因此任务仍按原顺序排队，准确率失败仍能触发重试，而校验器不会再根据错误的重叠时间误报并发超限。
